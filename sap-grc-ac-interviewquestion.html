📖 Fundamental Concepts
1
What is a Risk? (General & SAP GRC)
FundamentalsEasy
▼

A common opening question — answer in two layers: general, then GRC-specific.

📌 General:
Any event or activity that can cause a loss to an organization or may lead to fraud.
📌 In SAP GRC:
A combination of functions which, when assigned to a user, causes a loss. When a single user has access to two conflicting activities, this leads to a risk.
💡
Always give the GRC-specific answer after the general one. Layered answers show depth of knowledge.
2
What is a Function? What are Actions and Permissions?
FundamentalsEasy
▼
🔷 Function:
A set of actions and permissions that can be performed by a user. Example: Vendor Master Maintenance contains all T-codes and authorizations for vendor creation/maintenance.
⚡ Action:
Primarily a T-code, but can also be a Fiori App, Query, RFC Function Module, or Web Application.
🔑 Permission:
= Authorizations. Pulled automatically from SU24 when a T-code is added. Only mark change/create-level authorizations as Active — display-only access is not a risk.
💡
Mention the AND/OR condition in permissions — AND = both must exist; OR = either one triggers the risk.
3
How many types of Risks are there in SAP GRC? Explain each.
Risk TypesMedium
▼
⚔️
SOD Risk
Segregation of Duties
🔴
Critical Action
Sensitive T-code/App
🔐
Critical Permission
Sensitive Authorization
1️⃣ SOD: Two or more conflicting functions assigned to same user. Example: Create Vendor + Pay Vendor. Minimum 2 functions needed.
2️⃣ Critical Action: A single sensitive T-code (e.g. SE38, SE16) that should not be in production. Single function only.
3️⃣ Critical Permission: A critical authorization (e.g. S_DEVELOP with Activity 02) that must not be in production. Single function — permissions only, no actions. Adding actions causes a system error.
💡
SOD = multiple conflicting functions. CA & CP = single function with sensitive access. State this clearly.
4
What is a Rule Set? How many can be created?
Rule SetEasy
▼
📦 Rule Set:
A container of all generated rules. Default rule set = "Global". No limit on custom rule sets. Rules generate only for risks with Active status.
⚠️
Always verify risk status is Active before generating rules. Inactive risks are excluded.
5
What is the complete process of Risk Creation in SAP GRC?
ProcessImportant
▼
  1. Define Business Process — Finance, Procurement, Purchase etc. Used to organize reports.
  2. Define Rule Set — Use standard Global or create custom. Just provide name and description.
  3. Create Functions — Add T-codes (Actions) + Authorizations (Permissions). Mark only risky ones as Active. Set AND/OR conditions carefully.
  4. Create Risk — Risk ID, Description, Level, Type (SOD/CA/CP), assign functions, assign Rule Set, set Risk Owners.
  5. Generate Rules — Select risk → Generate Rules → Foreground or Background. Rules stored in Rule Set.
⚠️ Critical Permission Risk: The function must contain only permissions, no actions. Actions cause a system error.
✅ Remember: Risk creation alone is not enough. Rules must be generated for the risk to be detected in analysis.
6
How do you download/re-upload a Rule Set? How many files are downloaded?
Rule SetImportant
▼

Bulk changes → Download (select Connector Group) → Edit text files → Re-upload. Exactly 10 files are downloaded.

#FilePurpose

2FunctionsFunction master data

🚨 Leading Zeros Warning!
Values like 01, 02 lose leading zeros in Excel. Always format those columns as TEXT before editing. Truncated zeros corrupt the entire rule set.
💡
Always take a backup copy before editing. Edit only the working copy. Use the backup to revert if something goes wrong.
7
What is a False Positive Risk? How do you handle it?
Common IssuesMedium
▼
📌 Definition:
System flags something as a risk, but in reality it is technically not a risk. It is incorrectly identified.
✅ How to Handle:
  • Review the rule set definition for that risk carefully.
  • Check functions, actions, permissions, and AND/OR conditions.
  • Correct the configuration (deactivate irrelevant permissions).
  • Regenerate the rules and re-run risk analysis to verify fix.
8
How do you ensure the Rule Set stays up-to-date with system changes?
Common IssuesCritical
▼
🚨 Common Problem:
Changes made in Production but forgotten in Development/Quality → rule set discrepancies across DEV → QAS → PRD → risks fire in one system but not others.
✅ Best Practices:
  • Synchronize rule set changes across all landscapes (DEV, QAS, PRD) simultaneously.
  • Use a change management process — document and transport every change.
  • Schedule periodic audits to compare rule sets across systems.
  • Assign clear ownership to the GRC team for rule set maintenance.
💡
Mentioning landscape synchronization shows real-world project experience — differentiates experienced candidates.
9
Describe a scenario where you modified the standard rule set.
ScenarioMedium
▼
Option A – Modify via Custom Functions:
Create new custom functions → Add to the standard risk → Regenerate rules.
Option B – Modify Standard Function Directly:
Edit actions/permissions in the existing standard function → Activate/deactivate as needed → Regenerate rules.
💡
The choice depends on the business requirement. Always involve the process owner and document changes for audit.
10
SOD: Create Vendor + Pay Vendor — explain the risk and remediation.
ScenarioImportant
▼
🚨 Risk:
One person can create a fictitious vendor and pay them — classic fraud. This is a SOD Risk.
✅ Remediation:
  • Role Redesign: Remove one conflicting access from the user (preferred).
  • Mitigation Control: If business requires both accesses, assign a compensating control (e.g. periodic review, dual approval).
  • GRC Mitigation: Assign mitigation control in GRC with documented justification.

🔍 Risk Analysis Types
11
What are the different types of Risk Analysis available in SAP GRC?
Risk AnalysisEasy
▼
  • User Level — Reads all roles assigned to a user, compares against rule set, identifies user-level risks.
  • Role Level — Reads all T-codes and authorizations in a role, identifies if the role itself carries SOD/CA/CP risks.
  • Profile Level — Analyzes at the authorization profile level.
  • HR Object Level — Analyzes risks tied to HR objects (positions, jobs, org units).
💡
It is recommended that roles are clean (no SOD conflicts) because any role-level SOD risk will automatically create a user-level SOD risk for every user assigned that role.
12
Explain User Level Risk Analysis in detail.
Risk AnalysisEasy
▼
How it works:
  1. GRC reads all roles assigned to the user in the connected system.
  2. Compares the combined access (T-codes + authorizations) against the active rule set.
  3. Identifies if any SOD conflict, Critical Action, or Critical Permission risk exists for that user.
  4. Flags and reports the risk with details of conflicting roles and T-codes.
📌 Example:
User has Role A (Create Vendor T-codes) + Role B (Pay Vendor T-codes) → GRC identifies the SOD conflict across both roles and flags the user.
13
Explain Role Level Risk Analysis. Why is it recommended?
Risk AnalysisMedium
▼
Prerequisites: Run Authorization Sync for the role first — this syncs the role's authorizations into GRC.
How it works:
GRC reads all T-codes and authorizations in the role → compares against rule set → identifies:
  • SOD risk if role has T-codes for both conflicting functions.
  • Critical Action risk if role contains a sensitive T-code.
  • Critical Permission risk if role has a sensitive authorization.
🚨 Why Clean Roles Matter:
If a role has an SOD conflict → every user assigned that role automatically inherits the SOD risk. This is why roles must be designed to be clean and SOD-conflict-free.
14
I am modifying an existing role. How can I check if my changes will cause a risk BEFORE making them?
Risk AnalysisScenarioImportant
▼
✅ Use Role Level Simulation in NWBC:
  1. Navigate to Role Level Simulation in NWBC.
  2. Provide the existing role name.
  3. Add the T-codes/authorizations you plan to add, or mark the ones you plan to remove.
  4. Run the simulation — GRC compares the proposed changes against the rule set.
  5. Review the result: will it cause a new risk or not?
📌 Decision:
✦ Risk found → Do further modifications before proceeding.
✦ No risk → Proceed with actual role changes confidently.
💡
This is a proactive, best-practice approach. Mentioning simulation in interviews shows maturity in GRC usage.

16
A user has a risk. How do you identify the role, T-code, and whether the T-code was actually used?
ScenarioReportsImportant
▼
  1. Run User Level Risk Analysis for the specific user.
  2. Download the Detailed Report → identify the roles, functions, and conflicting T-codes.
  3. Check the Summary Report → see how many times the conflicting T-code was actually executed.
  4. Use this data to decide: remove the role, or apply a mitigation control.
🚨 Challenge with Detailed Report on Large Data:
For users with many risks, the detailed report can be extremely large → may fail to load or fail to download from NWBC.
✅ Solutions:
  • Run risk analysis in smaller chunks (subset of users at a time).
  • Use backend JAC spool download for large-volume extracts when NWBC download fails.
⚙️ Batch vs Online Risk Analysis
17
What is Batch Risk Analysis (Offline Risk Analysis)?
Risk AnalysisMedium
▼
📌 Also Called: Offline Risk Analysis. Used for large volumes of data without real-time connectivity.
  1. Run Repository Object Sync — syncs all users, roles, and profiles from connector system to GRC.
  2. Run Authorization Sync — syncs role authorizations from connector system to GRC.
  3. Once both sync jobs are successful, schedule Batch Risk Analysis via SPRO/background job.
  4. On completion, reports are generated and available for analysis in GRC.
💡
Both sync jobs must be successful before scheduling batch risk analysis — otherwise data will be stale or incomplete.

🔧 Rule Set Configuration
19
How do you set a default Rule Set for Access Requests? (Parameter 1021)
Rule SetScenarioMedium
▼
✅ Solution:
Use Parameter 1021 in SPRO/GRC configuration. Set the default rule set ID there → this rule set is automatically selected when an access request is raised and risk analysis runs on submission.
💡
Parameter 1021 is a commonly asked config parameter in interviews. Know its purpose clearly.
20
How to auto-select different Rule Sets based on Company Code during Access Requests?
Rule SetScenarioAdvanced
▼

Goes beyond simple parameter config — requires BRF+ (Business Rules Framework).

  1. Create a BRF+ attribute for Company Code.
  2. Write a BRF+ rule: If Company Code = 1000 → use Rule Set 1. If Company Code = 2000 → use Rule Set 2.
  3. Configure the BRF+ rule in SPRO GRC parameters.
  4. System now auto-selects the correct rule set based on user's company code — no manual selection needed.
💡
Knowing BRF+ integration with GRC is an advanced differentiator in interviews.
21
Should custom T-codes be included in the Rule Set? How do you check if a T-code is already in it?
Rule SetScenarioMedium
▼
📌 Decision:
It is a business decision.
✦ Reporting/Display T-code → Usually not required.
✦ Create/Change access T-code → Recommended to include.
✅ How to Check:
Use table GRFN_ACT_RULE.
Enter: Custom T-code + Connector → Execute → If records returned, T-code is already in the rule set.

23
How do you check if a custom T-code is part of the Rule Set using a table?
DB TablesScenarioEasy
▼
  1. Open table GRFN_ACT_RULE via SE16 or SE16N.
  2. Enter the custom T-code in the Action field.
  3. Enter the relevant Connector (system ID).
  4. Execute — if records returned, T-code is already in the rule set.
  5. If no records → T-code is not in the rule set → add it to the relevant function if required.

25
What do you do when the Detailed Report fails to load or download due to large data volume?
Common IssuesRisk AnalysisImportant
▼
🚨 Problem:
Running risk analysis for large numbers of users generates enormous data. Detailed report may fail to load in NWBC or throw errors during download.
✅ Solutions:
  • Run risk analysis in smaller batches — subset of users at a time.
  • Use backend JAC spool download — submit as background job, download output from spool.

26
What is the next step after identifying a Risk — Remediation or Mitigation?
Risk AnalysisFundamentalsMedium
▼
1️⃣ Remediation:
Fix the root cause — remove the conflicting access from the user/role. Eliminates the risk entirely.

Example: Remove the Pay Vendor role from a user who also has Create Vendor access.
2️⃣ Mitigation:
When business requires the user to have both accesses, implement a compensating control.

Example: Periodic manager review, dual approval workflow, activity monitoring. Assign a formal Mitigation Control in GRC with documented justification.
💡
Remediation is always preferred — it eliminates risk. Mitigation is a business-driven exception. This topic is covered in depth in the next video.
27
Why should roles be kept clean (SOD-conflict-free)?
Risk AnalysisScenarioBest Practice
▼
🚨 The Problem with Dirty Roles:
If a role contains an SOD conflict → every single user assigned that role automatically inherits the SOD risk → creates a large number of user-level violations that are difficult to remediate individually.
✅ Best Practice:
Design roles to serve a single business function. Avoid putting conflicting T-codes in the same role (Least Privilege Principle).

Use Role Level Simulation before adding T-codes to verify no new SOD is introduced.
